# Geospatial File Measurement API

A small FastAPI service that takes a shapefile (zipped) or a KML file, reads the
features inside it, and reports the area of polygons / length of linestrings in
real-world units (square meters / meters), not raw degrees.

Run it with:

```
./.venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

## Setup

You need Python 3.14-ish and the deps in `requirements.txt`.

```
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe -m uvicorn app.main:app --reload
```

The app listens on `http://127.0.0.1:8000` by default. It creates a SQLite file
`geo.db` next to the project root on first run (via a lifespan hook that calls
`init_db()`), so there's no separate migration step to run.

To run the test suite:

```
./.venv/Scripts/python.exe -m pytest
```

36 tests, covering the CRS/measurement math, both readers, and the API end to
end (including a deliberately corrupted zip to check it fails gracefully
instead of 500ing).

There's also `sample_data/` with a ready-made KML and a zipped shapefile you
can throw at the upload endpoint right away, generated by
`scripts/make_samples.py` (so you don't have to go find or build test fixtures
yourself).

## API

Three endpoints, plus a list endpoint and a health check.

### `POST /api/files/`

Multipart upload, field name `file`. Accepts `.zip` (zipped shapefile) or
`.kml`. Processing happens synchronously in the request - no background job,
so you get the full result back immediately.

```
curl -F "file=@sample_data/survey.zip" http://127.0.0.1:8000/api/files/
```

Response (201), this is a real captured response from running the app against
`sample_data/survey.zip`:

```json
{
  "id": "f88705c8c868",
  "filename": "survey.zip",
  "file_type": "shapefile",
  "feature_count": 2,
  "status": "COMPLETED",
  "crs": "EPSG:4326",
  "projected_crs": "EPSG:32630",
  "error": null,
  "created_at": "2026-10-08T08:39:46.828979"
}
```

If the extension isn't `.zip`/`.kml` or no file was attached, you get a 400,
not a crash. If the file parses as the wrong type (bad zip, missing `.shp`,
unparseable XML, whatever), the upload still returns 201 but with
`status: "FAILED"` and an `error` message - the thinking there is that
"you tried to upload something and I couldn't read it" is a legitimate,
recorded outcome, not a server error.

### `GET /api/files/{id}/`

File metadata. 404 if the id doesn't exist. Same shape as the upload response
above - `crs` is the source CRS (from the `.prj` for shapefiles, always
`EPSG:4326` for KML), `projected_crs` is whatever CRS was actually used to
measure.

### `GET /api/files/{id}/measurements/`

Per-feature breakdown. 404 if the file id doesn't exist. Real response for the
same shapefile upload above:

```json
{
  "file_id": "f88705c8c868",
  "features": [
    {
      "feature_index": 0,
      "geometry_type": "Polygon",
      "measurement_type": "area",
      "measurement_value": 111269.5498,
      "measurement_unit": "m2",
      "note": null,
      "properties": { "name": "St James's block" }
    },
    {
      "feature_index": 1,
      "geometry_type": "Polygon",
      "measurement_type": "area",
      "measurement_value": 115889.3022,
      "measurement_unit": "m2",
      "note": null,
      "properties": { "name": "Green Park block" }
    }
  ]
}
```

And uploading `sample_data/bangalore_sample.kml` (a polygon and a
linestring) gives a mix of `area` and `length`:

```json
{
  "file_id": "fe2ec5a29757",
  "features": [
    {
      "feature_index": 0,
      "geometry_type": "Polygon",
      "measurement_type": "area",
      "measurement_value": 240335.6563,
      "measurement_unit": "m2",
      "note": null,
      "properties": { "name": "Cubbon Park (made up boundary)" }
    },
    {
      "feature_index": 1,
      "geometry_type": "LineString",
      "measurement_type": "length",
      "measurement_value": 911.5652,
      "measurement_unit": "m",
      "note": null,
      "properties": { "name": "MG Road (made up route)" }
    }
  ]
}
```

Points come back as `measurement_type: "none"` with a null value - there's
nothing to measure on a point. Anything that fails to parse as a valid
geometry also comes back as `none`, with a short `note` saying why, instead of
breaking the whole upload over one bad feature.

### Everything else

`GET /api/files/` lists all uploaded files, newest first. `GET /health` just
returns `{"status": "ok"}` so you can check the process is alive.

## Architecture

```
app/
  main.py          FastAPI app, lifespan hook calling init_db()
  config.py        pydantic-settings, env var GEO_DB_URL etc
  database.py      engine, SessionLocal, get_db dependency
  models.py        File, Feature (SQLAlchemy ORM)
  schemas.py       FileInfo, FeatureMeasurement, MeasurementsResponse
  processing.py     process_upload() - the orchestration step
  crs.py           UTM zone picking + reprojection
  measurement.py   area/length calc on an already-projected geometry
  readers/
    shapefile_reader.py
    kml_reader.py
  routers/
    files.py       the three endpoints
```

**File processing flow**: the router gets the raw bytes off the upload,
decides shapefile vs KML off the extension, and hands everything to
`process_upload()`. That function picks the right reader, gets back a list of
raw features (shapely geometry + a geometry type string + a properties dict +
the source CRS), works out a target projected CRS once for the whole file,
reprojects each geometry into it, measures it, and builds the `File` +
`Feature` rows. Everything in one transaction - either the whole file ends up
`COMPLETED` with its features, or the exception gets caught and it ends up
`FAILED` with an error message and zero features. One bad feature inside an
otherwise-fine file doesn't abort the upload (that's handled inside
`measurement.measure()`, which returns `none` + a note instead of raising);
only a reader-level failure (can't even parse the file) marks the whole
upload FAILED.

**Measurement flow**: `measurement.measure(geom)` takes a geometry that's
already in a projected CRS and just reads `.area` or `.length` off it
depending on `geom_type`. Polygons and MultiPolygons get area, LineStrings and
MultiLineStrings get length, Points/MultiPoints get `none`, and anything
invalid or empty also gets `none` with an explanatory note. It doesn't know
or care about CRS - that's all handled upstream.

**CRS handling**: this is the part of the assignment I spent the most time
thinking about. Shapefiles tell you their source CRS via the `.prj` file
(or they don't, in which case I assume WGS84 and move on - a missing `.prj`
is common enough that failing loudly felt wrong). KML has no CRS field at all
because the spec says it's always lon/lat WGS84, so that's hardcoded.

Either way you end up with coordinates in degrees, and you can't measure area
or length in degrees in any way that means anything (a degree of longitude is
a very different distance near the equator than near a pole). So before
measuring anything, the geometries get reprojected into UTM. I pick the UTM
zone off the centroid of all the features in the file combined (average
centroid x/y), not per-feature - a file usually represents one area of
interest, and using one consistent CRS for every feature in it means the
measurements are comparable to each other. The zone math is the standard
`zone = int((lon + 180) / 6) + 1`, EPSG `32600 + zone` for the northern
hemisphere or `32700 + zone` for the southern.

If the source CRS turns out to already be projected (not geographic), I skip
all of that and just measure directly in whatever CRS it's already in -
reprojecting a British National Grid file into UTM just to reproject it again
would be pointless work and extra float error for nothing.

The reprojection itself goes through `pyproj.Transformer`, used with
`always_xy=True` to keep lon/lat ordering consistent (pyproj will silently
flip you into lat/lon axis order on certain CRS definitions otherwise, which
cost me a confusing hour before I added that flag explicitly). shapely 2.2
dropped `shapely.ops.transform` in favor of `shapely.transform`, which takes
the coordinate array directly instead of point-by-point - noticeably faster
on anything with more than a handful of vertices, since it avoids one Python
function call per point.

## Design decisions

**FastAPI over Django.** This is a small, stateless-ish API with no admin
panel, no auth, no templates - Django would be bringing a lot of furniture
into a one-room apartment. FastAPI's automatic OpenAPI docs and Pydantic
validation cover everything this assignment actually needs.

**pyshp + lxml instead of geopandas/fiona/GDAL.** This was the biggest call
in the whole project. I considered geopandas first since it would have made
the readers almost trivial. But getting GDAL (which fiona and geopandas both
sit on top of) to build cleanly on Windows with a recent Python turned into a
rabbit hole of wheel mismatches, and the assignment brief specifically wants
this done without those libraries anyway. Writing the shapefile and KML
parsing by hand with pyshp and lxml took longer, but I came out the other
side actually understanding the binary shapefile format and the KML schema
instead of trusting a library to hand me clean geometries. Shapely still does
the geometry math (area, length, validity checks) - no reason to hand-roll
that part.

**Synchronous processing.** Upload and measurement both happen in the same
request. For files this size that's milliseconds, and it means the client
gets a definitive answer (`COMPLETED` or `FAILED`) in one round trip instead
of having to poll a status endpoint. If this had to handle shapefiles with
tens of thousands of features, I'd move this to a background task (Celery, or
even just FastAPI's `BackgroundTasks` for something lighter) and add a
`PROCESSING` status in between. Didn't seem worth the complexity for the
stated scope.

**SQLite.** Single-file, zero setup, fine for a take-home. The SQLAlchemy
layer doesn't lean on anything SQLite-specific (no raw SQL, standard column
types), so swapping the `db_url` in config for a Postgres URL should work
without touching the models.

**One UTM zone per file, picked from the centroid.** Already covered above,
but worth restating as a decision: I considered picking a UTM zone per
feature instead, which would be marginally more accurate for a file that
spans multiple zones, but it would mean two features in the same file could
end up measured in different projections, which felt like it'd cause more
confusion than it solves for files of the size this assignment is aimed at.

## Learning and future scope

The CRS part took longer than I expected going in - I knew in the abstract
that "degrees aren't meters" but actually sitting down and picking a correct
UTM zone from a centroid, and remembering `always_xy=True`, made it concrete.
Writing the KML parser by hand also made me actually read the KML spec
instead of skimming it, which was useful - there's a decent amount of
Placemark/ExtendedData/SimpleData structure that's easy to not notice if a
library is quietly doing it for you.

If I kept going, the things I'd add next:

- A real identify-the-CRS path for shapefiles with no `.prj` at all, maybe by
  checking if coordinates look like they're in a plausible lon/lat range vs
  some other projected range, instead of just assuming WGS84.
- Background processing with a status endpoint for large files, mentioned
  above.
- Multi-geometry-type shapefiles are a format limitation I ran into while
  building the sample data - a single `.shp` can only hold one shape type, so
  "a shapefile with a polygon and a line" isn't really a thing you can upload
  as one file. The sample zip has two polygons instead; the KML sample covers
  the polygon + linestring mix.
- Pagination on `GET /api/files/` once there's enough files in the DB for
  that to matter.
